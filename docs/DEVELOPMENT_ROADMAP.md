# 开发路线图与阶段验收

## 1. 实施顺序

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| 1. 规划 | 本套架构文档、边界与风险清单 | 领域、数据归属、集成边界无冲突；院方确认范围 |
| 2. 架构基线 | 仓库结构、技术决策、CI 质量门禁 | 编译/lint/基础测试可重复；不启动生产服务 |
| 3. 数据模型 | ERD、数据字典、Flyway/Liquibase migrations | 迁移可从空库执行和回滚/修复验证；隐私字段已分类 |
| 4. API 契约 | OpenAPI、错误码、鉴权与版本策略 | 三端共享契约；兼容性和权限审查通过 |
| 5. 后端基础 | IAM、组织、异常、审计、存储、配置 | 登录、刷新、注销、RBAC、审计和安全测试通过 |
| 6. 管理后台 | 权限菜单、组织、医生、科室、CMS | API 数据权限生效；无医疗数据越权展示 |
| 7. 患者 Web | 首页、医生科室、就诊人、预约入口 | 移动/桌面可用、适老化检查、无敏感本地缓存 |
| 8. 小程序 | 登录、首页、预约、我的 | 微信能力真机验证；与 Web 使用同一业务 API |
| 9. 预约挂号 | 排班、库存、预约、取消、候补 | 10 个号源/1000 并发请求最多 10 成功；可补偿、可审计 |
| 10. 支付 | 订单、回调、退款、对账 | 验签、金额校验、幂等回调、退款状态机和沙箱测试通过 |
| 11. 报告 | LIS/RIS/PACS 受控查询、文件访问 | 对象级权限、短时 URL、访问审计和结构化报告验证通过 |
| 12. 消息 | 模板、站内信、订阅/短信通道 | 投递可追踪、重试可控、不泄露敏感内容 |
| 13. 医疗集成 | 标准 Port、厂商 Adapter、对账/补偿 | 契约测试、超时/重放/故障降级、测试环境联调通过 |
| 14. 综合测试 | 性能、安全、权限、回归、演练报告 | P0/P1 缺陷清零；关键链路测试与恢复演练通过 |
| 15. 部署上线 | 镜像、Compose、Nginx、运行手册 | 配置外置、无默认密码、监控告警、备份恢复验证通过 |

## 2. 主要技术风险与控制

| 风险 | 控制措施 |
|---|---|
| HIS 等厂商接口质量/口径不一 | 先签接口契约和主数据责任矩阵；Adapter 隔离、沙箱联调、对账 |
| 高并发挂号超卖 | Redis 原子预占 + 数据库条件更新 + 唯一/幂等约束 + 压测 |
| 支付异步与退款不一致 | 状态机、验签、回调去重、主动查询和日对账 |
| 过早微服务化 | 先模块化单体；以独立发布/扩缩容/数据主权为拆分证据 |
| 报告文件外泄 | 私有桶、短期签名、对象授权、下载水印（如院方要求）和审计 |
| 主患者重复或错配 | MPI/健康卡映射、人工核验和可追溯合并规则 |

## 3. 下一阶段建议

下一条任务建议进入“阶段 2–4 的基础设计”，先确定仓库初始化方式、MySQL migration 工具（推荐 Flyway）、身份认证边界、组织/患者/排班的最小 ERD 与 OpenAPI 骨架。开始预约或支付编码前，必须取得院方的挂号规则、收费口径、取消退款规则和外部接口测试条件。
