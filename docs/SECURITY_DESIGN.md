# 安全、权限与医疗隐私设计

## 1. 安全基线

外网入口使用 TLS、WAF、限流、DDoS 防护及可信代理链；内部服务也应使用受控网络与最小端口暴露。密码采用强哈希（Argon2id 或经评审的 BCrypt）；验证码设频率、次数、设备/IP 风险阈值；登录失败限速/锁定并提供安全告警。JWT 为短期访问令牌，Refresh Token 旋转、可撤销、设备绑定并仅以安全 Cookie 或平台安全存储承载。

所有 API 做服务端认证、授权、参数校验、对象级权限校验和速率限制。SQL 均使用参数绑定；富文本白名单净化并配置 CSP；Cookie 场景启用 CSRF 保护；上传文件做类型/大小/内容检测、恶意文件扫描、私有存储与下载鉴权。密钥存环境专用 Secret/KMS，永不写入仓库、前端包或普通日志。

## 2. RBAC + ABAC 数据权限

权限模型由 `用户—角色—权限` 完成菜单、按钮、API 的粗粒度授权；再以属性策略完成组织、院区、科室、患者关系、就诊状态、授权有效期、访问目的和数据等级的细粒度判定。

| 角色示例 | 可访问范围 |
|---|---|
| 患者 | 本人及已授权就诊人的数据 |
| 接诊医生 | 有效就诊关系、授权科室和时间范围内的必要数据 |
| 科主任 | 本科室经批准的汇总/业务数据，不自动获得所有病历正文 |
| 财务人员 | 应收、支付与退款，默认不见诊断和报告正文 |
| CMS 运营 | 内容与媒体资产，不见患者、订单和医疗数据 |
| 系统管理员 | 配置与账号管理；不因技术权限自动获得医疗数据阅览权 |

敏感查看、导出、批量查询、权限变更、支付退款等操作需要用途、二次验证或审批（具体阈值由院方制度配置）。紧急访问（break-glass）必须显式声明原因、限时授权、即时审计和事后复核，不能作为普通查询后门。

## 3. 医疗隐私与审计

遵循最小必要、目的限定、默认保护与可追责：前端只请求页面必要字段，默认脱敏；患者可见其授权记录；受保护报告只通过鉴权接口生成短期下载地址。审计至少记录“谁、何时、因何目的、以何权限、访问了谁的何类数据、结果如何”，并同样记录拒绝事件。

日志按 system/access/login/operation/audit/error/payment/integration 分类，采用结构化、脱敏输出。安全事件、支付回调失败、异常批量导出、越权访问和库存异常应告警。日志、备份、对象存储、消息队列均需访问控制、加密和留存策略。

## 4. 安全验证与上线门禁

上线前至少完成 SAST/依赖漏洞扫描、接口鉴权与对象越权测试、注入/XSS/上传/会话测试、限流和验证码防刷测试、支付验签与回调重放测试、权限矩阵测试、审计完整性验证、备份恢复演练、渗透测试（按院方要求）及高危问题清零。不得以“前端隐藏按钮”替代授权验证。

## 5. STEP 2 实施补充

STEP 2 已定义 Access/Refresh Token 轮换、BCrypt 密码哈希、账户锁定、显式 CORS 白名单、Trace ID、后端权限注解、私有 MinIO Bucket、受保护短期下载地址及不含请求体的审计基础设施。普通日志不得输出 `password`、`Authorization`、JWT、Refresh Token、完整身份证和诊疗正文；该规则由代码审查、静态扫描与后续日志采集脱敏策略共同保证。

## STEP 5.1 患者身份补充

患者敏感字段采用外部密钥 AES-GCM 加密及 HMAC 精确检索；后台和患者令牌采用不同主体与 audience。患者对象授权在服务层验证成员归属，防止 IDOR；患者后台列表由服务端脱敏，审计不写入完整手机号、证件号、密文、哈希或验证码。

## STEP 5.2 预约补充

预约接口只接受患者令牌；服务层将预约行的 `patient_id` 与令牌主体逐次比较，拒绝跨患者详情、确认和取消。锁号使用数据库唯一键和参数绑定 SQL，不授予患者后台预约权限。预约 DTO、状态历史和普通日志不包含身份证、手机号、加密内容、HMAC、验证码或 Token；迁移历史保留 Trace ID 以支持安全审计。

## STEP 5.4 恢复与密钥补充

患者数据加密键和检索 Hash 键必须来自运行时受保护配置，启动时拒绝空值、非 Base64 或不足 32 字节的密钥；密钥不进入源码、API、审计、普通日志或前端构建产物。停诊批量取消仅写预约状态、库存、状态历史与审计所需的 Trace ID，不记录患者敏感字段。

MySQL 是预约事实与库存的唯一权威；Redis 被视为可丢失缓存。恢复或对账只读检出差异，禁止以缓存覆盖 MySQL 或在没有人工确认的情况下自动修复预约库存。数据库外键阻止预约和状态历史成为孤儿记录。

## STEP 6.1 支付安全

资金状态只接受提供方验证结果；不相信客户端金额，不允许管理端手动设 SUCCESS。
回调限制原始 body 16 KiB、进程级限流、HMAC 恒定时间验签、时间窗、nonce/eventId 唯一约束与交易号唯一约束。金额/币种异常不会更改资金状态并保留摘要审计。
TEST bean/路由使用 `!prod & (dev | test)`，registry 双重限制；真实渠道未配置时 fail closed，无自动回退。
禁止原始回调、JWT、完整手机号/身份证或支付密钥进入 DTO、交易流水和日志。
密钥仅环境/受限文件路径注入；前端无真实支付 SDK 或商户密钥。配置与边界详见 PAYMENT_DESIGN.md。

## STEP 6.2 退款安全

退款金额不接受患者取消请求指定，后端以支付事实与已成功/已保留退款计算。退款回调沿用原始字节大小限制、时间窗、HMAC 验签、eventId/nonce 重放保护，并额外校验退款号、提供方退款号、支付引用、金额和币种。退款与对账日志只保存业务编号、分单位金额、状态和 Trace ID，不保存回调原文、令牌、密钥或支付凭证。

## STEP 6.3 体验层边界

能力接口只公开通道代号和测试标识，绝不返回支付密钥、签名材料、回调原文或访问令牌。患者列表以 patient_id 强制隔离；财务汇总、订单与退款查询使用 DataScope 过滤。前端只展示金额、状态和经 allowlist 的订单字段。
## STEP 6.4 支付安全

商户号、AppID、API v3 Key、私钥路径/Secret Mount、平台证书和支付宝密钥只从运行时环境或 Secret Store 获取；仓库、前端和小程序不保存真实值。Provider 仅访问固定 HTTPS 网关，不关闭 TLS 校验，也不允许请求参数决定上游 URL。HTTP 调试日志不得输出完整签名、私钥、Authorization、回调原文、支付 token 或个人敏感信息。

回调必须基于原始 body 及 Provider 时间戳/nonce/签名验证；事件唯一性与持久化状态共同防重放。请求 body 有大小限制，验签/解析失败只返回通用业务错误，不泄露第三方堆栈或密钥信息。

## STEP 7.1 门诊访问安全

患者只能以令牌主体签到和查询本人候诊，不能操作队列。医生接口不接受 doctorId，并逐条校验实际出诊医生。公共队列 DTO 不包含患者身份、预约或医疗信息；诊室与队列操作有审计，医生打开 Encounter 另写医疗访问审计，日志不保存身份证、手机号或令牌。

## STEP 7.2 临床文书安全

临床 DTO 使用显式 allowlist，不能直接序列化实体、密钥或签名内部字段。病历签署的 SHA-256 内容摘要只用于完整性验证，不是加密或 CA 法律签章；正文、诊断快照和过敏反应不进入应用日志或审计正文。病历阅读需要治疗关系或独立临床审计权限，并在 `clinical_access_audit` 写入资源、行为、操作者、Trace ID 和时间。

## STEP 7.3 处方与药房安全

签署处方对处方头和项目快照计算 SHA-256，签署后禁止普通更新；药师不能修改医生药品内容。提交时重新检查医院目录和药品安全结果，BLOCK 失败关闭，WARNING 需要专门权限、原因和审计。库存预占、释放与发药采用 MySQL 事务和带余额条件更新，库存/批号不能为负；过期或停用批号不能新发药。患者 DTO 不包含库存、审方内部原因和安全规则细节，日志与药品审计不保存病历正文、令牌或密钥。

## STEP 7.4 诊断安全

诊断报告和医嘱使用确定性 SHA-256 防篡改，FINAL 版本不允许普通更新，修订另建版本。患者 DTO 排除危急规则、检验质控、内部 Provider Payload、PACS 凭据、员工备注和审计；危急告警必须显式确认。生产环境关闭 Test Provider，未配置真实集成时失败关闭。
